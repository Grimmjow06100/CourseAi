# Course AI - Contributor Instructions

## Project scope

Course AI generates structured IT courses with an asynchronous AI pipeline. The repository contains:

- `backend-go`: the only backend, written in Go;
- `frontend`: the React/Vite client;
- PostgreSQL development infrastructure at the repository root.

Prefer explicit, maintainable code over abstractions that only reduce line count. Preserve the dependency rule and keep generated code isolated.

## Backend architecture

The Go backend follows a clean architecture dependency direction:

```text
infrastructure -> contract <- service -> domain
                         domain <- contract
cmd/api -> all concrete adapters (composition root only)
```

- `internal/domain`: entities, value objects, invariants and state transitions. No infrastructure imports.
- `internal/contract`: ports, repository interfaces, use-case interfaces and shared application errors.
- `internal/service`: application orchestration and authorization. Depends only on `contract`, `domain` and `shared`.
- `internal/infrastructure`: Gin, Clerk, OpenAI, PostgreSQL, prompts, workers and the system clock.
- `internal/db/sqlc`: generated database code. Never edit it manually.
- `cmd/api`: configuration and dependency construction. Business rules do not belong here.

The detailed package map and request flows are documented in `backend-go/docs/architecture.md`.

## Backend stack and rules

- Go 1.27+
- Gin HTTP router
- PostgreSQL with pgx/pgxpool
- SQL migrations with Goose
- Queries and typed database methods generated by sqlc
- Clerk bearer authentication on every `/api` route
- OpenAI Responses API with strict Structured Outputs
- Durable PostgreSQL jobs with leases, heartbeats, retries and idempotency

Rules:

1. Keep business invariants in `domain`, orchestration in `service`, interfaces in `contract`, and vendor-specific code in `infrastructure`.
2. Define interfaces at the consuming boundary. Add compile-time implementation assertions for infrastructure adapters.
3. Keep transaction boundaries in services through `contract.UnitOfWork`; repositories perform persistence, not workflow orchestration.
4. Never hand-edit `internal/db/sqlc`. Change migrations or `internal/db/queries`, run `sqlc generate`, then adapt repositories.
5. Every schema change requires a new forward Goose migration. Do not rewrite an applied migration.
6. Enforce strict JSON schemas for all LLM responses and validate the mapped domain objects before persistence.
7. Wrap errors with operation context and `%w`. Do not expose provider, SQL or stack-trace details in HTTP responses.
8. Keep unit tests beside the package under test. PostgreSQL integration tests belong in `tests/integration/postgres`.
9. Add GoDoc to exported APIs when their contract, lifecycle or constraints are not obvious from the name.
10. Run formatting, static checks and focused tests after each change; run the full verification suite before completion.

## Backend verification

From `backend-go`:

```powershell
gofmt -w <changed-go-files>
go vet ./...
staticcheck ./...
go test -count=1 ./...
go test -race ./...
sqlc vet
make test-integration
```

When database queries change, also run `sqlc generate` and verify that only expected generated files changed.

## Frontend stack and rules

- React with Vite and functional components
- TanStack Query v5 for server state
- TanStack Router
- Clerk for authentication
- Tailwind CSS
- React Hook Form and Zod

Validate user input with Zod before API submission. Keep API DTO types aligned with the OpenAPI document exposed by the backend.
